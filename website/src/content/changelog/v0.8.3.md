### Highlights

- New `requires_bridge: true` field on catalog entries — declarative flag for vendor endpoints whose local install path is fundamentally broken on Claude Code's auth model
- Installer now prints a `REQUIRES BRIDGE: enable '<name>' in claude.ai` status instead of attempting a doomed local registration
- Pre-existing bug in `--items <single-id>` resolution fixed (the items loop was dropping the last entry due to a missing trailing newline)

### What Dave hit

`pm` bundle install. His other connectors (Gmail, Calendar, Drive, Granola) routed cleanly through the claude.ai bridge. Slack didn't — the bridge wasn't enabled for Slack on his claude.ai account, so the installer fell through to the local install path: `claude mcp add slack https://mcp.slack.com/mcp`. On first OAuth, his Claude Code returned:

> Slack's auth server doesn't support Dynamic Client Registration. Only accepts pre-registered OAuth clients tied to a specific Slack App.

His diagnosis was correct. Claude Code's MCP client uses RFC 7591 Dynamic Client Registration to bootstrap OAuth for `mcp_remote` endpoints. Slack's official endpoint requires pre-registered clients tied to a Slack App you create in api.slack.com. DCR isn't supported. The local install path was always going to fail.

It works for him on the bridge because claude.ai's Slack connector ships with a pre-registered OAuth App that handles auth on the user's behalf — that's what `mcp__claude_ai_Slack__*` is. So the catalog assumption "if the bridge isn't there, install locally" was wrong specifically for Slack.

### What changed

`data/plugin-catalog.yaml` schema now supports `requires_bridge: true` on the `claude_code` block. When set, the installer:

1. Still checks for the bridge first (unchanged).
2. If the bridge isn't detected, prints `REQUIRES BRIDGE: enable '<name>' in claude.ai` instead of running `claude mcp add`.
3. The new Phase 6.6 summary section lists every bridge-required item with a direct link to https://claude.ai/settings/connectors.

The field is intentionally conservative — only flag entries whose local install has been *confirmed* broken via a failed OAuth attempt, not anything that might theoretically be broken. Audit-the-others is not in this release. Future cases get added one at a time as users report them.

Also fixed: a pre-existing silent failure in `--items <single-id>` that dropped the last entry from the items parser. One-line fix.

### Why this matters

Three back-to-back hotfixes in three hours from one user's install. Each surfaced a different layer of the same general gap: the catalog assumed too much about local OAuth (v0.8.3), the installer didn't handle the recovery path (v0.8.2), and the original install leaked infrastructure files (v0.8.1). All three are now closed. The next user who hits any one of these will get a clear path forward from the installer or the skill, not a Slack message to the maintainer.

### Upgrade

`/thinkos-update --pull` picks up v0.8.3 normally on existing installs. Anyone running a fresh `pm` or `eng` install now sees `REQUIRES BRIDGE: enable 'Slack' in claude.ai` instead of a broken OAuth attempt.
