### Highlights

- **First external contribution** on the repo, from Dave Drager (Technical Lead at Think Company)
- **New `tracked_projects[]` array in `vaults.json`** — session-capture's filter now unions vault paths with tracked code-repo roots, fixing the silent-drop on typical "code outside the vault" installs
- **Fresh installs now auto-migrate manifest v1 → v2** — retires v0.8.2's recovery flow as the hot path; recovery now only fires on stale pre-v0.8 installs
- **Three silent v0.8 regressions caught**: filter default wrong for typical users, `__REPO_ROOT__` substitution missing, `flock(1)` doesn't ship on macOS

### What Dave caught

Dave installed v0.8 this morning and his session-capture launchd job was exiting silently every fire. Three bugs underneath, all my v0.8 work:

1. **My `--project-filter` default was wrong for the typical user.** I shipped a filter that only matched sessions whose `cwd` was under a registered vault path. But most users keep code OUTSIDE the vault (vault = notes, repos = `~/Code/`). On Dave's install, every session was dropped silently for hours.

2. **`__REPO_ROOT__` never substituted in `install-session-capture.sh`.** I added the token to the plist template in v0.8 (WP-38) but forgot to substitute it in the install script. `WorkingDirectory` was the literal string `__REPO_ROOT__`. Harmless because launchd-invoked scripts use absolute paths anyway — but ugly and a footgun for future work.

3. **`flock(1)` isn't on macOS.** My v0.8.0 WP-41 ledger append wrapped writes in `flock` for concurrent-writer safety. macOS uses fcntl; BSD-flock isn't bundled. Every session-capture run printed `flock: command not found` before falling through to the append.

His PR introduces a new `tracked_projects[]` array in `~/.thinkos/vaults.json` for code-repo roots that aren't vaults. The filter now accepts the union of `vaults[].path` ∪ `tracked_projects[].path`. Backward-compatible (absent array = today's behavior). Replaces the silent zero-match exit with a timestamped stderr warning pointing the user at `tracked_projects` or `--all-projects`. Adds a "Recent no-match events" surface in `/thinkos-autosave status` so the new stderr is useful instead of noisy. Guards `flock` with `command -v` and falls back to a plain append (safe because launchd serializes scheduled fires by job label).

### And the architectural improvement

Fresh v0.8 installs landed at manifest v1, but `/thinkos-autosave`, `/thinkos-update`, and `/thinkos-capture-setup` all expect v2 fields. That's the same bug Chris hit on his pre-v0.8 install — and the reason v0.8.2 added a recovery flow. Dave's fix runs the existing idempotent v1→v2 migrator inline at the end of setup, so fresh installs never land at v1.

This makes v0.8.2's recovery flow the cold path. Fresh installs don't need recovery; the recovery only fires on stale pre-v0.8 installs where the user upgraded through `/thinkos-update`. Cleaner shape, less recovery surface area.

### Why this is v0.9.0 instead of v0.8.5

The hotfix series (v0.8.1–v0.8.4) framed real-user bugs as patches to the v0.8 hardening release. Dave's PR is structurally bigger:

- New `tracked_projects[]` contract in `vaults.json` is additive functionality, not a fix for a regression
- First external contribution warranted a version-number marker
- Three silent regressions caught + one architectural improvement is more than a typical patch-release

### Open follow-up (v0.9.1 or v1.0)

Dave's no-match stderr warning fires on every launchd run with zero matched sessions. Could grow `session-capture.err` over time. Single-line timestamped messages + surfaced usefully in `status` are reasonable mitigations for now; worth folding into the v0.7-era log rotation if it becomes annoying.

### Upgrade

`/thinkos-update --pull` picks up v0.9.0 normally. Fresh installs from this point land at v2 manifest automatically. Existing installs that hit Chris's stale-manifest case still use v0.8.2's recovery flow.
