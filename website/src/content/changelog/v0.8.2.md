### Highlights

- `/thinkos-update` Step 0 now scans four common checkout locations before declaring "no repo found"
- New Step 0a — when no valid checkout exists, the skill walks the user through clone + re-run setup via `AskUserQuestion`
- Recovery is idempotent: vault content is untouched, manifest is rewritten with `repo_path` set, slash commands and CLAUDE.md block are refreshed to latest

### The chain that produced this hotfix

Chris reported a bug at 11:13 EDT (leaked plist templates in the vault). v0.8.1 shipped at 11:30. My v0.8.1 message to Chris said "run `/thinkos-update --pull` to pick up the fix." Chris tried that; his agent came back: _"there's no git repo on my machine, the install manifest doesn't have a `repo_path`, where's the Think OS repo I should clone from?"_

For someone on v0.8.x with a current manifest, my advice was right. For Chris — v0.7.x install, v1 manifest with no `repo_path`, original checkout deleted at some point — `/thinkos-update` couldn't find anything to operate on and the skill told the agent to "stop." Dead-end where there should have been a recovery path.

### What changed

`/thinkos-update` Step 0 (locating the repo) used to try `repo_path` from the manifest, fall back to one hardcoded default (`~/code/think-os`), and stop if neither was found. Now it scans four common locations (`~/Code/think-os`, `~/code/think-os`, `~/Documents/think-os`, `~/Documents/Think/think-os`) and explicitly checks for `.git/` so a tarball download doesn't look like a valid checkout.

If none of those work, the new Step 0a takes over instead of stopping. It uses `AskUserQuestion` to offer four chips (recommended default, alternative location, custom path, cancel) and then runs:

```bash
git clone https://github.com/dhirajsapkal/think-os.git "$TARGET"
cd "$TARGET" && bash scripts/thinkos-setup.sh --products claude-code --yes
```

Setup is idempotent — it skips existing vault files, rewrites the `~/.claude/CLAUDE.md` block to the latest content, re-copies all slash commands, and writes a fresh manifest with `repo_path` correctly set. The user's vault is never touched.

After recovery completes, the skill tells the user to restart Claude Code (Cmd+Q) and that `/thinkos-update` will work normally for future releases.

### Why this matters

Three releases in a single day driven by one user's bug-report cascade. The leaked plists confused his agent. My fix message confused his agent. The update flow didn't have a recovery path for his specific install state.

Each release closes the specific failure he hit AND the broader pattern it represents. The next user in any pre-v0.8 state will get walked through recovery by the skill, not by the maintainer in Slack.

### Upgrade

If you already have a working repo, `/thinkos-update` picks up v0.8.2 normally. If you're in Chris's situation (no repo / missing `repo_path`), `/thinkos-update` now handles the recovery itself — just invoke it and pick a clone location when prompted.
